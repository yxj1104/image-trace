# 规划自检报告

对 `PLAN.md` v1.0 的逐项实测复核 · 2026-11-17

复核原则：凡规划中出现的数字，都必须有实测支撑；无法实测的，必须标记为未验证。本文档只记录**发现的问题**与**修正依据**，不复述已正确的部分。

---

## 一、错误清单（按严重程度排序）

### E1 · 致命：单一 pHash 方案在三种真实场景下失效

**规划原文（§4.1）：**

> 距离 ≤ 4：同画面（高置信）
> 距离 5-10：疑似同画面

**实测结果（真实 PSD 缩略图 vs 真实导出图，含人为变形）：**

| 查询形态 | 纯 pHash 命中前 10 | 判定 |
|---|---|---|
| 无改动 | 49/50 (98%) | 可用 |
| 裁四周 5% | 49/50 (98%) | 可用 |
| 裁四周 10% | 44/50 (88%) | 勉强 |
| **旋转 90°** | **8/59 (14%)** | **失效** |
| **旋转 180°** | **0/59 (0%)** | **完全失效** |
| **手机截图（含界面边框）** | **14/59 (24%)** | **失效** |

**原因：** pHash 基于 DCT 低频系数，对**位置变化**极度敏感。旋转会重排整个低频矩阵；加边框会整体压缩有效内容区，改变频率分布。

**修正方案（已实测验证）：两阶段检索 + 查询侧旋转校正**

| 查询形态 | 两阶段（pHash 召回 50 → ORB 重排） | + 旋转校正（试 4 方向） |
|---|---|---|
| 裁 10% | 48/50 (96%) | — |
| 旋转 90° | 42/59 (71%) | **59/59 (100%)** |
| 旋转 180° | 52/59 (88%) | **59/59 (100%)** |
| 手机截图 | 50/59 (85%) | 需配合自动裁边 |

**结论：v1.0 把「分块哈希」列为 P4 可选，把 ORB 完全遗漏，是方案级错误。ORB 必须进 P1。**

### E2 · 严重：文件总量估算错 3 倍，且统计口径错误

**规划原文（§3.4、§1.1）：**

> 文件总量 53,000（图片 + 源文件）
> 首次建库 10-15 分钟

**实测（`os.walk` 全盘无深度限制）：**

```
不排除任何目录：        59,209
排除系统目录后：        59,209
排除软件/缓存目录后：   18,219  ← 真实有效量
```

**差异来源：`F:\腾讯电脑管家软件搬家\软件搬家` 一个目录就有 33,084 个目标格式文件**，其中 17,989 个 JPG + 13,868 个 PNG 全部是 Illustrator 2019 安装包自带的示例素材、图标、启动画面。这些是纯噪音，一旦入索引会严重污染检索结果。

**真实分布（排除后）：**

| 格式 | 数量 | 格式 | 数量 |
|---|---|---|---|
| jpg | 8,466 | ai | 82 |
| psd | 5,354 | jpeg | 69 |
| png | 3,017 | gif | 34 |
| webp | 919 | cdr | 27 |
| pdf | 192 | eps | 24 |
| | | svg | 18 |

**修正：** 总量 18,219，排除规则必须包含软件搬家目录、WXWork 程序目录、ps2026、CorelDRAW 自带素材、Kugou、JianyingPro、adobeTemp。

### E3 · 严重：AI 渲染速度低估 7.5 倍

**规划原文（§3.1）：**

> AI 预览：pypdfium2，36ms/个

**实测（全量 30 个样本）：**

```
平均 271 ms/个
最慢：4,628 ms（徽章奖杯素材.ai，24.1 MB）
      1,631 ms（新疆.ai，349.8 MB）
最快：1 ms（部分文件几乎是空壳）
```

**36ms 是 3 个样本得出的假象。** 方差极大，与文件复杂度正相关，无法用文件大小预测。

**修正：** 按 271ms 估值。199 个 AI 文件 → 54 秒，影响不大，但必须在进度条上体现「大文件会卡住」，否则用户会以为程序死掉。

### E4 · 中等：PDF 与 AI 存在未记录的失败率

**规划原文：** 未提及失败率。

**实测：**

| 类型 | 成功 | 失败 | 失败率 |
|---|---|---|---|
| AI | 39/40 | 1 | 2.5% |
| PDF | 33/40 | 7 | **17.5%** |

失败全部为 `PdfiumError`（加密、损坏、非标准结构）。

**修正：** 必须有 `extract_error` 字段记录，UI 上对这些文件显示「无法预览」而非静默跳过。PDF 失败率接近两成，不能忽略。

### E5 · 中等：同名配对比例算错（23% → 40%）

**规划原文（§1.3）：**

> 实测 1,207 对，占 PSD 总量 23%

**实测（全三盘，无深度限制）：**

```
真实配对：2,187 对 / 5,437 PSD = 40.2%
```

23% 这个数字来自早期只扫 E/F 两盘且限制深度的粗测。

**修正：** 40%。这意味着**接近一半的 PSD 能靠文件名直接配对**，这个信号的价值比 v1.0 估计的更高，应该在 UI 上更突出。

### E6 · 中等：存储体积估算无依据

**规划原文（§9 待确认事项 4）：**

> 缩略图缓存约 1-2 GB

**实测：**

```
缩略图 240px / JPEG q75：19.3 KB/张  →  18,219 张 = 344 MB
ORB 特征（≤300 点）：     8.8 KB/张  →  18,219 张 = 157 MB
SQLite 元数据：                        →  约 20 MB
────────────────────────────────────────────────
合计：约 520 MB
```

**修正：** 520 MB。1-2 GB 高估了一倍以上。

---

### E7 · 轻微：误判率被过度估计

**规划原文：** 隐含假设「距离近 = 同一张图」。

**实测（250 个随机 PSD 两两比对，共 29,890 对）：**

```
距离 ≤ 10 的配对：3 对，占 0.01%
这 3 对分别是：
  泰享游1121.psd  ↔  泰享游1212.psd      （距离 2）
  夏日活动0711.psd ↔ 夏日活动0827.psd （距离 2）
  主视觉红3.psd  ↔  主视觉红.psd      （距离 2）
```

**这三对不是误判，是真阳性** —— 同系列海报换了个日期，视觉几乎一致。

**修正：** 误判风险极低（0.01%），但揭示了另一个问题：**距离近不等于同一个文件**。如果同一画面有 5 个迭代版本，UI 必须全部列出并显示差异，让用户自己判断改哪一版。这是 v1.0 完全没考虑的需求。

## 二、v1.0 遗漏但实测证明必要的功能

| # | 功能 | 实测收益 | v1.0 位置 |
|---|---|---|---|
| **F1** | **ORB 两阶段重排** | 旋转 14% → 71%，截图 24% → 85% | 完全没有 |
| **F2** | **查询侧旋转校正（0/90/180/270）** | 旋转场景 → 100% | 完全没有 |
| **F3** | **查询侧自动裁白边** | 加边框 3% → 95% | 完全没有 |
| **F4** | 同系列多版本并列展示 | 防止只给出一个「最佳匹配」而漏掉真正的目标版本 | 完全没有 |

**F3 的实测细节（值得单独记一笔）：**

```
加白边 10% 的图 —— 原方案命中率：    3% (1/39)
加白边 10% 的图 —— 自动裁白边后：   95% (37/39)
```

自动裁边实现只需要 15 行代码（取四角像素估算背景色 → 差值掩码 → getbbox），却能救回一个完全失效的场景。**这是投入产出比最高的一个改动，应在 P1 就做。**

## 四、修正后的建库时间估算

```
PSD      5,354 × 114 ms  = 610 s
其他图  12,865 ×  40 ms  = 515 s
AI/PDF/CDR 301 × 271 ms  =  82 s
────────────────────────────────
单进程合计                 1,207 s ≈ 20 分钟
8 进程（加速 3.31x）         ≈ 6 分钟
```

v1.0 的「10-15 分钟」偏高，但因为总量算错（5.3 万 vs 1.8 万），两个错误互相抵消，最终数字反而接近。**这是巧合，不是估算正确。**

## 五、本次自检未能验证的项

诚实标注，不掩饰：

1. **大库规模下的 ORB 重排耗时。** 实测单次 ORB 比对 0.03ms，理论 6 万库暴力比对 2.1 秒。但这个数据来自 200 个小库的模拟，真实 1.8 万库未跑通。
2. **同一海报的不同版本之间，用户如何高效区分。** E7 揭示了这个需求，但「怎么在 UI 上展示微小差异」没有方案。
3. **微信实际压缩参数。** 用 1280px/q35 模拟，真实微信可能是 q50-70 或做过智能压缩，命中率可能更好也可能更差。
4. **8 进程在机械硬盘上的表现。** 实测在 SSD 上做的，E/F/G 盘类型未确认。
5. **界面实际观感。** 规划里的布局草图未做可交互原型，自绘控件的可用性未验证。

## 六、结论

**v1.0 的架构判断（原地索引、放弃 CLIP、PSD 内部提取、不用库型工具）全部成立。**

**v1.0 的技术细节有 7 处错误，其中 E1（单 pHash 失效）如果不修正，工具在「同事发来手机截图」这个最高频场景下会失败——而这恰好是用户描述的主要使用场景。**

已按上述修正重写 `PLAN.md` 至 v2.0。
