规划文档 v2.0 · 2026-11-17
（v1.0 的 7 处错误已修正，依据见 `AUDIT.md`）

---

## 1. 问题定义

### 1.1 真实场景

同事（客户、销售、产品）发来一张图，要求「改一下」。我需要找到这张图的**源文件**（PSD / AI / CDR），才能动手。

难点不在「改」，在「找」：

- 源文件和交给别人的导出图是**两个独立文件**，目录可能相隔几个盘
- 源文件名和导出图文件名通常不一致（`海报A_终稿_v3.psd` → `微信图片_20240612.jpg`）
- 同事发来的常常是**手机截图**（带聊天界面边框、可能被旋转）或**微信二次压缩图**
- 时间久了记不得是哪个项目、哪个客户、哪一版

### 1.2 三个需求

| 编号 | 需求 | 本质 |
|---|---|---|
| R1 | 同事给图，搜出这张图的**源文件在哪** | 反向溯源 |
| R2 | **以图搜图**，找原图 | 视觉匹配 |
| R3 | **筛选分类**，按条件缩小范围 | 结构化过滤 |

### 1.3 决定成败的事

**视觉相似只能找到「同一画面的图」，找不到「产生这张图的源文件」。** 源文件和导出图在文件系统上无任何关联。

必须四路信号叠加：

| 信号 | 覆盖什么 | 实测可靠性 |
|---|---|---|
| **A. 内嵌缩略图提取** | 直接命中源文件本身 | PSD 100%、CDR 100%、AI 97.5%、PDF 82.5% |
| **B. 同目录同主名配对** | 从导出图跳到源文件 | 2,187 对，占 PSD 总量 40% |
| **C. 两阶段视觉检索** | 命中导出图 / 无源文件的图 | pHash 召回 + ORB 重排 |
| **D. 查询侧预处理** | 修复截图、旋转、边框 | 加边框 3%→95%，旋转 14%→100% |

**A 是本工具与所有现成工具的根本差异。** 素刀、Krokiet、Eagle 都不索引 PSD 内部——它们只看得到文件的外表。我们看内部。

## 2. 核心设计理念

### 2.1 结果不是「一堆相似的图」，而是「图 + 它的源文件」

常规以图搜图工具返回图片列表。对本场景这是错的——用户要的不是 20 张长得像的图，是**一个明确的源文件路径**。

```
[查询图] ──检索──▶ ┌────────────────────────────────────┐
                   │ 组 #1  置信度 高                     │
                   │  导出图  活动主视觉0110.jpg           │
                   │  源文件  活动主视觉0110.psd  ◀ 目标    │
                   │  同系列  3 个版本（0110/1212/0108） │
                   └────────────────────────────────────┘
```

**一个「组」= 一张画面 + 它的全部关联文件。**

### 2.2 同一画面多版本必须并列

实测发现：同系列海报换日期后，指纹距离仅 2/64（`泰享游1121.psd` ↔ `泰享游1212.psd`）。

这不叫误判，这是**真阳性**。如果只给一个「最佳匹配」，用户会改错版本。

因此：距离 ≤ 6 的全部文件都作为候选并列展示，标注修改时间与尺寸差异，由用户判断。

### 2.3 匹配必须可解释

每张卡片说明**为什么匹配**：

- `缩略图指纹 3/64 · ORB 0.46`
- `同目录同主名`
- `宽高比一致 1080×1920`
- `修改时间相差 3 天`

### 2.4 不做的事

- 不做云端、不上传任何文件
- 不做语义 / 自然语言搜索（R1-R3 不需要，且 1.8 万张上代价过高）
- 不做文件搬移、不做库导入——所有文件原地不动
- 不做删除、不做批量重命名

## 3. 技术架构

### 3.1 技术选型

| 层 | 选择 | 实测依据 |
|---|---|---|
| 索引器 | Python 3.13 | — |
| 存储 | SQLite 单文件 | 1.8 万记录，含特征约 520 MB |
| 服务 | 标准库 `http.server` | 零依赖 |
| 前端 | 原生 HTML/CSS/JS | 零构建，全自绘 |
| 一级指纹 | pHash 64bit | 3ms/张，用于快速召回 |
| 二级匹配 | ORB + Lowe 比值 | 8.2ms/张建特征，0.03ms/次比对 |
| PSD 预览 | 手写 resource 解析 | 114ms/个 |
| AI 预览 | pypdfium2 | 271ms/个（方差极大，见 §3.6） |
| CDR 预览 | `zipfile` 取 thumbnail.bmp | 27/27 成功 |

**为什么不用 CLIP：** 诉求是「找**同一张图**的源文件」，是精确匹配不是语义相似。CLIP 会把「同类风格的不同海报」排在前面制造噪音，且 1.8 万张 CPU 推理需数小时。

数据表保留 `embedding` 字段作为扩展位。

### 3.2 两阶段检索管线（核心修正）

```
查询图
  │
  ├─ ① 预处理
  │    ├─ 自动裁掉纯色边框（取四角估背景色 → 差值掩码 → getbbox）
  │    └─ 生成 4 个旋转版本（0° / 90° / 180° / 270°）
  │
  ├─ ② 一级召回：pHash
  │    对每个旋转版本，算 pHash，在库中取距离最近的 50 个
  │    4 个版本取并集，去重 → 候选池
  │
  ├─ ③ 二级重排：ORB
  │    对候选池每个文件，用 Lowe 比值法（0.75）算特征匹配分
  │    得分 = 好匹配数 / min(特征点数)
  │
  └─ ④ 输出
       按 ORB 分排序，附加文件系统信号（同主名 / 同目录 / 时间邻近）
```

**实测效果（真实 PSD 缩略图 vs 真实导出图）：**

| 查询形态 | 纯 pHash@10 | 两阶段@10 | +旋转校正 |
|---|---|---|---|
| 无改动 | 49/50 | 49/50 | — |
| 裁 5% | 49/50 | 49/50 | — |
| 裁 10% | 44/50 | 48/50 | — |
| 加白边 10% | 低 | 高 | — |
| 旋转 90° | 8/59 (14%) | 42/59 (71%) | **59/59 (100%)** |
| 旋转 180° | 0/59 (0%) | 52/59 (88%) | **59/59 (100%)** |
| 手机截图 | 14/59 (24%) | 50/59 (85%) | 待配合裁边 |

**误判基线：** 随机 120 对不同图，ORB 分中位 0.003，p95 0.014，max 0.200。阈值取 **0.10** 可区分。

### 3.4 索引流程

```
1. 遍历目录（配置根路径 + 排除规则）
   排除：$RECYCLE.BIN / System Volume Information / 360RecycleBin
         Program Files / AppData
         腾讯电脑管家软件搬家   ← 单目录 33,084 个噪音文件
         WXWork / ps2026 / CorelDRAW 自带素材 / steam / KuGou
         JianyingPro Drafts / adobeTemp / _codex_archive

2. 分派提取器
   .psd          → image resource 1036 缩略图
   .ai/.pdf      → pypdfium2 首页
   .cdr          → zip 内 metadata/thumbnails/*.bmp
   .png/.jpg/... → PIL
   .eps/.svg     → P3 处理，先标记

3. 计算双指纹
   ├─ pHash 64bit（一级召回）
   ├─ ORB 特征（≤300 点，二级重排）
   ├─ 宽高比 + 主色调 3 色（筛选与辅助判定）
   └─ 缩略图落盘（240px / JPEG q75）

4. 写入 SQLite + 缩略图缓存

5. 配对（全库扫完后）
   ├─ 同目录同主名（忽略扩展名）—— 实测 2,187 对
   ├─ 去版本后缀后同名
   └─ pHash ≤ 6 且宽高比一致 → 同画面组
```

### 3.5 性能估算（全部实测）

```
真实文件量    18,219（排除噪音后）
PSD           5,354 × 114 ms  = 610 s
其他图       12,865 ×  40 ms  = 515 s
AI/PDF/CDR      301 × 271 ms  =  82 s
──────────────────────────────────────
单进程                          1,207 s ≈ 20 分钟
8 进程（加速 3.31x）              ≈ 6 分钟
```

**存储：**

```
缩略图 19.3 KB × 18,219 = 344 MB
ORB 特征 8.8 KB × 18,219 = 157 MB
SQLite 元数据            =  20 MB
────────────────────────────────
合计                      ≈ 520 MB
```

**查询延迟：** 6 万哈希最近邻 0.5 ms；ORB 单次比对 0.03 ms。

### 3.6 已知异常与不确定性

| 项 | 情况 | 应对 |
|---|---|---|
| **AI 渲染速度方差极大** | 平均 271ms，最慢 4,628ms（24MB 文件），最快 1ms | 进度条显示当前文件名；超时 15s 后跳过并标记 |
| **PDF 失败率 17.5%** | `PdfiumError`（加密/损坏/非标准） | `extract_error` 字段记录，UI 显示「无法预览」 |
| **AI 失败率 2.5%** | 同上 | 同上 |
| **PSD 缩略图分辨率低** | 最长边通常 160px | 实测对 pHash 与 ORB 均足够（pHash 只用 32×32） |
| **PSD 缩略图宽高比** | 与画布一致，偏差中位 0.17%，最大 1.69% | 可直接用缩略图尺寸代表画布 |

## 4. 指纹方案细节

### 4.1 pHash 的实测边界

| 变形 | 距离（/64） | 结论 |
|---|---|---|
| 微信压缩 640px/q30 | 0 | 完美 |
| 微信压缩 480px/q25 | 0 | 完美 |
| 缩放 50% | 0 | 完美 |
| 裁四周 2% | 中位 4，最大 18 | 可用 |
| 裁四周 5% | 中位 12 | 需 ORB 补救 |
| 裁四周 10% | 中位 22 | 失效 |
| 底部加文字带 10% | 中位 6 | 可用 |
| 底部加文字带 14% | 中位 10 | 勉强 |
| 四周加白边 10% | 中位 24 | 失效（但裁边后恢复） |
| 旋转 90° | — | 失效（旋转校正后恢复） |
| 旋转 180° | — | 完全失效（旋转校正后恢复） |

**判定阈值：**

- pHash ≤ 4：高置信同画面
- pHash 5-10：候选，交 ORB 判定
- pHash > 10：不进候选池（由旋转版本的召回兜底）

### 4.2 ORB 的实测边界

| 变形 | ORB 分中位 | 命中（≥0.10） |
|---|---|---|
| 无变形 | 1.000 | 94% |
| 裁 5% | 0.413 | 91% |
| 裁 10% | 0.382 | 91% |
| 裁 20% | 0.103 | 53% |
| 裁 30% | 0.019 | 3% |
| 加白边 5% | 0.467 | 94% |
| 加白边 15% | 0.361 | 91% |
| 裁 5% + 加白边 10% | 0.457 | 94% |

**不同图基线：** 中位 0.003，p95 0.014，max 0.200。

**阈值取 0.10，对应误判率 p95 以下。** 但注意 max 0.200 说明存在极端误判可能（同色系极简海报），需配合 pHash 与宽高比交叉验证。

### 4.3 预处理：自动裁白边

投入产出比最高的一个改动：

```
加白边 10% 的图 —— 不裁边：   3% 命中 (1/39)
加白边 10% 的图 —— 裁边后：  95% 命中 (37/39)
```

实现约 15 行：

```python
def autotrim(im, tol=14):
    g = im.convert('L'); w, h = g.size
    corners = [g.getpixel((0,0)), g.getpixel((w-1,0)),
               g.getpixel((0,h-1)), g.getpixel((w-1,h-1))]
    bg = max(set(corners), key=corners.count)
    mask = ImageChops.difference(g, Image.new('L', (w,h), bg)).point(
        lambda p: 255 if p > tol else 0)
    bb = mask.getbbox()
    if not bb: return im
    if (bb[2]-bb[0]) < w*0.3 or (bb[3]-bb[1]) < h*0.3: return im  # 裁太狠说明估错
    return im.crop(bb)
```

**注意：** 入库时不裁边（保留原始画面），只在**查询时**对查询图裁边。因为库里的图本身就是干净的，裁边可能误伤纯色底设计稿。

### 4.4 分块哈希（不采用）

实测多尺度中心裁切取最小距离的方案**效果反而更差**：

```
裁 5%  —— 多尺度：44% 命中（原方案 47%）
裁 10% —— 多尺度： 0% 命中（原方案 0%）
```

原因是 pHash 对裁切的不变性极差，靠试多尺度无法补救。**ORB 才是正确解法，分块哈希从规划中移除。**

## 5. 数据模型

```sql
CREATE TABLE files (
    id            INTEGER PRIMARY KEY,
    path          TEXT UNIQUE NOT NULL,
    name          TEXT NOT NULL,
    stem          TEXT NOT NULL,
    ext           TEXT NOT NULL,
    kind          TEXT NOT NULL,          -- source | export | other
    size          INTEGER,
    mtime         INTEGER,
    width         INTEGER,
    height        INTEGER,
    aspect        REAL,
    phash         TEXT,                   -- 64bit hex
    orb           BLOB,                   -- ORB 描述子
    palette       TEXT,                   -- JSON: 3 个主色
    thumb_path    TEXT,
    thumb_kind    TEXT,                   -- embedded | rendered | native
    extract_error TEXT,
    group_id      INTEGER,
    indexed_at    INTEGER
);

CREATE TABLE groups (
    id          INTEGER PRIMARY KEY,
    cover_id    INTEGER,
    source_id   INTEGER,
    confidence  REAL,
    reason      TEXT
);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);
```

## 6. UI 规范

### 6.1 硬性约束：全部自绘，禁止原生控件

| 禁止 | 替代 |
|---|---|
| `<select>` | 自绘弹出面板 + 键盘导航 |
| `checkbox` / `radio` | 自绘方形勾选块 / 圆点 |
| `number` 的 spinner | 自绘步进 + 可拖动数值 |
| `input[type=color]` | 自绘色环 |
| 原生滚动条 | 自绘细条，悬停加粗 |
| 原生 `title` 气泡 | 自绘 tooltip 层 |
| `alert` / `confirm` | 自绘模态 |
| 原生文件选择框 | 自绘拖拽区 |
| 日期选择器 | 自绘输入 + 相对时间快捷键 |

实现：CSS `appearance: none` + `::-webkit-scrollbar` 覆盖 + 自定义 DOM。不引入任何 UI 框架。

| **P3** | 筛选器 + 详情 + 多版本展示 | 完整交互 | 主观：是否比翻目录快 |
| **P4** | 增量索引、颜色筛选、EPS/SVG | 长期可维护 | 日常使用一周的漏检统计 |

**P1 必须先验证准确率再动 UI。** 指纹在你的真实数据上不行，UI 做多漂亮都没用。

**P1 内必须包含：** 自动裁白边、旋转校正、ORB 重排。这三项是实测证明的必需项，不是优化项。

## 8. 风险与未验证项

| 风险 | 影响 | 应对 |
|---|---|---|
