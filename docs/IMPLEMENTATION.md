## 六、修掉的两个实现 bug

### B1 路径重复索引（已修）

`os.walk('E:/')` 产出的 dirpath 是 `E:/a\b`，`os.path.join` 后仍是混合分隔符。  
早期为了「去掉结尾斜杠」做了 `rstrip('/\\')`，把根路径改成 `E:`，导致  
`os.path.join('E:', 'a')` = `E:a` —— 盘符相对路径，排除规则全部失效。

后果：中途一版索引把 `F:\腾讯电脑管家软件搬家` 下 3 万个噪音文件全吃进去了，  
记录数从 1.8 万虚涨到 4.8 万。已修复：

```python
def _norm_root(root):
    p = os.path.normpath(os.path.abspath(root))
    if p.endswith(':'):
        p += os.sep        # 盘符根必须保留分隔符
    return p
```

并加了 `EXCLUDE_PREFIX` 前缀匹配，抓 `_codex_archive_2026-11-16` 这类带日期的目录。

### B2 SQLite 整数溢出（已修）

pHash 是 64 位无符号，但 SQLite INTEGER 是有符号 64 位。存 `phash_bits` 时  
`OverflowError`。改为只取低 63 位（`& 0x7FFFFFFFFFFFFFFF`）用于快速比对，  
精确距离仍用十六进制字符串算，不影响排序。

`console=False`，双击不弹黑框。日志写到 `data/app.log`。

### 打包后踩到的三个坑（都已修）

**1. 相对导入失效 → 索引开不了**

`core/indexer.py` 原本写 `from .. import trace as cli`，在打包环境里  
`trace` 是入口脚本不在包路径中，报 `attempted relative import beyond top-level package`。  
修法：把 `walk_files` / `build_record` / `worker` 从 `trace.py` 抽到  
`core/scanner.py`，CLI 和索引作业都 import 它。

**2. 增量索引误删全库 → 数据被清空（最严重）**

首次测试「只索引一个子目录」时，把另外 18,174 条记录全删了。  
根因：删除判定写成了「磁盘上找不到的已知记录就删」，没有限定在本次扫描的根目录内。

```
修复前：known - current  → 全库范围内比对
修复后：known ∩ 本次roots - current  → 只在扫描范围内比
```

新增 `_under_any(path, roots)` 做前缀归属判断。修复后实测：  
只索引 `D:/workspace/project-a`（322 个文件），总记录从 18,197 保持 18,197，删除 0 条。

**3. 打包版多进程静默失败 → 新文件进不来**

`multiprocessing` 在 PyInstaller 窗口模式下会崩（无控制台 + 缺 `freeze_support()`）。  
现象：进度条显示「1/1 完成」，但库里没有新记录，日志里只有奇怪的 `IndexJob` 报错。

修法两条：

- `app.py` 入口加 `multiprocessing.freeze_support()`
- `IndexJob` 在 frozen 环境默认 `jobs=1`（单进程），不尝试多进程

增量更新通常只有几十个文件，单进程足够。全量重建会慢（22 分钟 → 更长），  
但打包版用户不需要频繁全量重建。

## 十一、P4 完成（2026-11-19）

### SVG / EPS 纳管

原本 `DEFERRED_EXTS = {'eps','svg','indd'}` 直接跳过，现在只剩 `indd`
（InDesign 需要专用 SDK，不做）。

**SVG**：用 `resvg_py`（Rust 渲染引擎，自带依赖，不需要系统装 cairo）。

选型过程（都实测过）：

| 方案 | 结果 |
|---|---|
| cairosvg | ❌ 依赖系统 `libcairo-2.dll`，Windows 默认没有 |
| svglib + reportlab | ❌ 渲染后端要 `rlPyCairo`，同样依赖 cairo |
| **resvg_py** | ✅ `svg_to_bytes(svg_path=..., width=512)`，9–52 ms/个 |

实测 3,134 个 SVG（含噪音目录）→ **3,132 成功（99.94%）**，失败 2 个是
`resvg_ValueError`（畸形文件）。排除噪音后实际入库 18 个。

**EPS**：两种格式分别处理。

- DOS EPS（魔术字节 `C5D0D3C6`）：32 字节头里有 PS / WMF / TIFF 三段偏移，
  内嵌 TIFF 就是现成预览图
- 纯 PostScript（`%!PS-Adobe`）：没有预览，需要 Ghostscript，本项目不引入

内嵌 TIFF 有个坑：**Pillow 直接 `Image.open` 会失败**（IFD 写在文件末尾，
且缺 Pillow 期望的必需 tag）。但它的结构其实是未压缩单 strip，按 IFD 里的
宽高、通道数、StripOffsets 手工拼字节就能出图 —— `/extract/eps.py` 的
`_decode_tiff` 做了这件事。

实测 24 个 EPS：**11 成功**（DOS EPS 有内嵌 TIFF）、12 个 `ps_only`、
1 个 `no_preview`。

### 文件名搜索

新增顶栏搜索框，配 `/api/list?q=` 和 `/api/suggest?q=` 两个接口。

**语法**：

| 输入 | 行为 |
|---|---|
| `海报` | 文件名或路径包含「海报」 |
| `海报 psd` | 空格分隔 = AND，两个词都要命中 |
| `.psd` | 按扩展名搜 |
| `泰国 海报 2024` | 三个词同时出现 |

**排序**（在 SQL 里做，不在 Python 里）：

```sql
ORDER BY (INSTR(LOWER(name), LOWER(?)) = 0) ASC,   -- 文件名命中优先于仅路径命中
         INSTR(LOWER(name), LOWER(?)) ASC,          -- 命中位置越靠前越好
         LENGTH(name) ASC,                          -- 名字越短越精确
         mtime DESC
```

**为什么必须在 SQL 里排**：最初写在 Python 里对 `j.items` 排序，
但那时结果已经被 `LIMIT` 截断了 —— 只重排了第一页，第二页开始顺序是错的。
验证方法：`offset=297` 那页的命中位置应该是单调不减的，改之前不是。

**踩到的 SQL 坑**：`INSTR` 对不命中的返回 0，不是大数。所以
`ORDER BY INSTR(...)` 会把「只在路径里出现」的文件排到最前面 —— 完全是反的。
要用 `(INSTR(...) = 0) ASC`，让「名字命中」的排前面。

**搜索建议**：`/api/suggest` 从文件名和目录名两路取，界面支持
↑↓ 选择、Enter 确认、Esc 清空。建议项高亮命中的字符片段。

**快捷键**：`Ctrl+K` / `Cmd+K` 聚焦搜索框，`Esc` 清空。

### 尺寸字段修正（P4 发现的旧 bug）

早期实现把**缩略图尺寸**存进了 `width`/`height`。PSD 的内嵌缩略图通常只有
74×160，于是界面上显示「74×160」而真实画布是 1080×2340 —— 对设计师来说
这是明显错误的数字，会让人怀疑整个工具的可信度。

修正：`core/scanner.py` 新增 `_real_size()`，按格式读真实画布尺寸：

| 格式 | 来源 | 成本 |
|---|---|---|
| PSD | 文件头第 14–22 字节 | 几乎为 0（不解析图像） |
| AI / PDF | pypdfium2 页面尺寸 | 一次文档打开 |
| PNG/JPG/... | PIL `Image.size` | 只读头 |
| SVG | `viewBox` 前 2KB | 只读 2KB |
| CDR | 无可靠来源 | 回退缩略图尺寸 |

**注意 `aspect` 必须与 `width/height` 一起修**，否则宽高比筛选会全错
（旧数据 aspect 来自缩略图，与新尺寸不自洽）。

存量迁移脚本：`tools/fix_sizes.py`，实测修正 **16,732 条**，未变 1,455 条
（这些本来就是位图，尺寸没错），读不到 63 条，耗时 6.3 分钟。

修正后校验：`ABS(aspect - width/height) > 0.002` 的记录为 **0 条**。

## 十二、资源管理器右键菜单（2026-11-19）

### 能力

| 右键位置 | 菜单项 | 行为 |
|---|---|---|
| 任意图片文件（PSD/JPG/PNG/...共 14 种） | 用溯源找源文件 | 对这张图直接以图搜图，界面展示结果 |
| 文件夹 | 在溯源中搜索 | 加入索引范围并立刻开始索引 |
| 文件夹空白处 | 在溯源中搜索 | 同上（用 `%V` 代替 `%1`） |
| 磁盘（C:/D:/E:...） | 用溯源索引此磁盘 | 同上 |

### 实现方式

**全部写 `HKEY_CURRENT_USER`，不需要管理员权限。**

```
HKCU\Software\Classes\SystemFileAssociations\.psd\shell\ImageTrace
HKCU\Software\Classes\Directory\shell\ImageTrace
HKCU\Software\Classes\Directory\Background\shell\ImageTrace
HKCU\Software\Classes\Drive\shell\ImageTrace
```

**为什么按扩展名逐个注册，而不是挂在 `*\shell`：**
挂 `*` 会对所有文件类型生效，包括 .txt / .exe / .zip —— 一个找图工具
出现在所有文件的右键菜单里是骚扰。按扩展名注册只在这 14 种图片格式上出现。

**命令形式：**

```
"溯源.exe" --from-shell --search "%1"      文件
"溯源.exe" --from-shell --add-root "%1"    文件夹 / 磁盘
"溯源.exe" --from-shell --add-root "%V"    文件夹背景
```

**exe 路径必须加引号** —— 装在 `Program Files` 这类带空格的目录时，
不加引号资源管理器会把路径拆成两段，命令直接失效。这是第一版漏掉的。

### 交互流程

```
右键点击 → exe 被调用
  ├─ 已有实例在跑 → 通过本地 HTTP 接口把动作交给它，不新起进程
  └─ 没在跑 → 先起服务，等就绪（最多 12 秒）再发动作
        ↓
   POST /api/shell-action  {action, path, total, top}
        ↓
   浏览器打开 → 前端轮询 /api/pending → 拿到动作 → 渲染结果 / 打开设置
```

**轮询不能「取一次就删」。** 右键会额外开一个新标签页，旧标签页也在轮询，
谁先拿到就消费掉，旧页面会误以为没动作。改成服务端保留最近一条并带
`_seq` 时间戳，前端记住自己处理过的序号去重。

### 界面开关

在「索引设置」面板里加了「在资源管理器右键菜单中显示」开关，
一个自绘 switch。开启后显示「已注册 14 种图片格式 + 文件夹 + 磁盘」。

不用去注册表里手改，也不用单独跑脚本。

### 实测

| 项 | 结果 |
|---|---|
| 注册 16 个位置（14 格式 + 文件夹 + 磁盘） | 全部成功，0 失败 |
| 注册表实际内容 | 命令路径正确、带引号 |
| 打包版 `--search` 端到端 | exe 返回 4.6s，前端标题变「以图搜图结果」，2 个结果正确 |
| 打包版 `--add-root` | 目录加入 roots，触发索引 |
| 卸载 | 删掉 17 个键（含背景右键），无残留 |
| 不需要管理员 | 当前非管理员账户，全部成功 |

### 未验证

- **真实在资源管理器里右键点击**：我通过 `subprocess` 模拟了完全相同的命令行，
  但没有真的用鼠标在文件夹窗口里点。Windows 有 shell 缓存，注册后可能需要
  重启资源管理器或注销才刷新 —— 这个行为未实测。
- Windows 11 的「显示更多选项」二级菜单里的显示效果
- 中文菜单文字在某些语言区域设置下的截断情况

## 十三、粘贴预览框 + 原生窗口（2026-11-19）

### 粘贴/拖入预览框

原来顶栏那个「拖图搜索」只是个虚线按钮，粘完图就看不到粘的是什么。
现在改成真正的预览态：

```
空态：  [ ↑ 拖图搜索 ]                    168 × 34
有图：  [🖼] 活动主视觉.jpg            ×  208 × 42
            已搜到 2 个
```

| 元素 | 行为 |
|---|---|
| 缩略图 | 30×30，圆角，直接显示粘贴/拖入的那张 |
| 文件名 | 单行省略，头部优先（`direction: rtl`） |
| 状态行 | 「比对中…」→「已搜到 N 个」/「没有匹配」/「搜索失败」（红色） |
| **×（右上角）** | 取消搜索，清空预览，回到全部文件 |
| 点框本身 | 换一张图（打开文件选择器） |

状态文案变化：比对中显示琥珀色，成功是强调绿，失败是警示红。
`×` 定位在**右上角**（`position: absolute; top: 2px; right: 2px`），
不是垂直居中 —— 按用户截图的要求。

### 原生窗口

**默认不再是浏览器。** 双击 exe 打开的是一个真正的 Windows 窗口：
有标题栏、能最小化/最大化、能拖拽缩放、关掉就退出进程。

用的是 **pywebview + WebView2**（Windows 自带 Edge Chromium 内核），
不是 Electron：

| 方案 | 体积代价 | 说明 |
|---|---|---|
| **pywebview** | +14 MB | 复用系统 WebView2，渲染与浏览器一致 |
| Electron | +150 MB | 自带整个 Chromium |
| 打包浏览器 | 0 | 但体验是「网页」，不是应用 |

窗口几何会记住：上次的大小和位置存到 `data/window.json`，下次还原。

**最小化时会写坏配置。** 实测窗口最小化后 `win.width/height` 变成
160×28，坐标变成 (-32000, -32000) —— 这是 Windows 的哨兵值。
直接存会导致下次启动是个角落里的小条。`save_geometry()` 现在做三层过滤：
尺寸小于最小值、坐标 ≤ -10000、宽高为 0，任意一条命中就跳过本次保存。

**兜底定时保存**：每 8 秒存一次。用户从任务管理器强杀进程时
`closed` 事件不触发，靠定时器至少保住最后一次正常尺寸。

### 回退路径

```
溯源.exe                  → 原生窗口（默认）
溯源.exe --browser        → 强制浏览器
溯源.exe --window         → 强制原生窗口
```

机器上没装 WebView2（Win10 可能没有）时，`_can_use_window()` 返回 False，
自动退回浏览器模式，不会卡死。

### 实测

| 项 | 结果 |
|---|---|
| 预览框空态宽度 | 168px |
| 预览框有图宽度 | 208px，缩略图 `display: flex`，× 为 `grid` |
| 预览框状态文案 | 「已搜到 2 个」正确 |
| × 位置 | 右上角（top 2px / right 2px） |
| 原生窗口创建 | `EnumWindows` 检测到标题「溯源」，尺寸 1360×880 |
| WebView2 内核 | 19 个子进程，说明页面真的在渲染 |
| 窗口内页面 | title 正确、300 张卡片、状态栏「已索引 18,250 个文件」 |
| 几何持久化 | `window.json` 写入 `{"w":1360,"h":880,"x":26,"y":26}` |
| 打包版自检 | 13 项全过（新增 `core.desktop` 检查） |

### 未验证

- 打包版在未安装 WebView2 的机器上的回退行为（本机有，无法测）
- 窗口在高 DPI 缩放（150%/200%）下的实际观感
- 多显示器拖到第二块屏幕后位置还原是否正确

## 十四、Office 文档支持 + 应用图标（2026-11-19）

### 支持范围

新增 doc / docx / docm / ppt / pptx / pptm / xls / xlsx / xlsm。
按本机实测（排除噪音目录后）：

```
docx  251    doc  135    pptx  29    xlsx  3    docm  1
─────────────────────────────────────────────────
合计  419 个
```

全部归为 `kind = source` —— 它们是可编辑的源文件，
和 PSD 一样属于「同事让你改、但你先得找到」的东西。

### 四层回退

Office 文档没有统一的内嵌预览图，只能分层试：

| 层 | 方法 | 覆盖 |
|---|---|---|
| 1 | **Windows Shell 缩略图** | 系统装了对应处理器的格式（PDF/PSD/AI 都很快，0–75ms） |
| 2 | **OOXML 包内 `docProps/thumbnail.*`** | docx/pptx/xlsx，Word 保存时会生成，不保证有 |
| 3 | **OLE `\x05SummaryInformation` 缩略图流** | 老 .doc，需要按 [MS-OLEPS] 解属性集 |
| 4 | **Word / WPS COM 导出 PDF 再渲染** | 兜底，1.7s/个，本机实测 100% 成功 |

**Shell 缩略图这条路是本轮最有价值的发现。** 一个 COM 调用覆盖所有格式，
而且结果和用户在资源管理器里看到的一致 —— 不会出现「我明明在文件夹里见过
缩略图，工具里却搜不到」。

调用链：
```
SHCreateItemFromParsingName → IShellItemImageFactory.GetImage
→ HBITMAP → GetDIBits → PIL
```

**这里踩了一个 ctypes 的硬坑。** `GetImage` 的第二个参数 `SIZE` 是
两个 LONG 打包成的 64 位值，**按值传**而不是拆成两个参数：

```python
# 错：拆成两个 c_int
get_image(factory, w, h, flags, byref(hbmp))
# → OSError: access violation writing 0x0000000000000009
#   （0x9 是 flags 的值被写进了 phbm 指针位置，参数错位了）

# 对：打包成 c_int64
packed = (size & 0xFFFFFFFF) | ((size & 0xFFFFFFFF) << 32)
get_image(factory, packed, flags, byref(hbmp))
```

### Office 必须串行

多进程处理 Office 会失败，实测错误 `-2147023170 远程过程调用失败`。原因：

1. COM 对象不能跨进程共享
2. 多个进程同时拉起 Word，彼此的 COM 调用会互相踩
3. 甚至单个 Word 实例复用也不行 —— 处理第二个文件就挂

所以 `IndexJob._index_items()` 把 Office 文件摘出来走单进程，
每个文件独立 Word 实例，处理完立刻 `Quit()`：

```python
office_todo = [t for t in todo if t[1] in OFFICE_EXTS]
other_todo = [t for t in todo if t[1] not in OFFICE_EXTS]
if office_todo:
    self._index_items_single(db, office_todo)
todo = other_todo
```

代价：**1.7 秒/个**。421 个 Office 文档约 12 分钟。但增量更新时通常
只有几个新文件，用户感知不到。

### comtypes 的两个坑

**坑一：`CreateObject` 不能用关键字参数传 `clsctx`。**
WPS 的 COM 服务器只注册了默认组合，传 `CLSCTX_LOCAL_SERVER` 起不来。

**坑二：`Documents.Open` 也必须按位置传参。**
comtypes 的 dynamic Dispatch 不支持关键字参数：

```python
# 错
app.Documents.Open(path, ReadOnly=True, AddToRecentFiles=False)
# → TypeError: Dispatch.__getattr__.<locals>.caller()
#   got an unexpected keyword argument 'ReadOnly'

# 对（Open 签名：FileName, ConfirmConversions, ReadOnly, AddToRecentFiles）
app.Documents.Open(os.path.abspath(path), False, True, False)
```

## 应用图标

主色 **#00DA7C**（用户指定），三段渐变 `#38F09B → #00DA7C → #00B667`。

造型：白色放大镜，镜片内是「图片」的通用符号 —— 山形 + 太阳圆点。
一眼能读出「在这个东西里找图」两层含义。

小尺寸验证：

| 尺寸 | 可辨度 |
|---|---|
| 256 / 128 | 山形、太阳、镜框都清楚 |
| 48 | 山形可辨，太阳略小但还在 |
| 32 | 放大镜轮廓成立，山形可辨 |
| 16 | 只剩「白圈 + 绿块」，但轮廓仍有辨识度 |

**第一版被我自己否掉了**：右侧加了两条装饰横线（暗示文件名列表），
32px 以下全糊成噪点，反而降低辨识度。删掉后干净很多。

生成方式：`tools/make_icon.py` 从 SVG 逐尺寸渲染，手工写 ICO 结构。

**为什么不用 Pillow 的 `save(format='ICO', sizes=[...])`：**
它会拿一张大图重采样出小尺寸，16px 边缘会糊。逐尺寸单独渲染，
每个尺寸都是原生清晰的矢量光栅化。

ICO 内含 7 帧：16 / 24 / 32 / 48 / 64 / 128 / 256。

| 位置 | 用法 |
|---|---|
| `溯源.exe` 文件图标 | PyInstaller `icon=` 参数 |
| 任务栏 / 标题栏 | `webview.start(icon=...)` |
| 浏览器标签页 | `<link rel="icon" href="/static/icon.png">` |

### 图标微调：太阳改为 #FFD015

第一版太阳用的是深墨绿 `#0B3D2C`，在白底镜片里像个黑点，不读作「太阳」。
改成 `#FFD015`（用户指定）后：

- 512 / 256：金黄圆点在白色镜片里明确是「太阳」，与绿色背景形成暖冷对比
- 48：仍清楚，是图标里唯一的高饱和暖色，反而成了记忆点
- 32：缩小到约 3px，但黄色比绿色背景亮，仍能看见
- 16：几乎不可辨，但不影响整体轮廓识别

同时把半径从 12 调到 13，保证小尺寸下至少占 2 个像素。

## 十五、详情面板大图预览（2026-11-24）

### 问题

右侧详情面板点 PSD 只显示灰色占位图标 —— 因为 `/api/file` 只认位图扩展名，
遇到 PSD / AI / CDR / Office 一律 `_serve_placeholder()`。而这正是最需要预览的
格式：面板的用途就是确认「这是不是我要改的那个 PSD」。

### 分格式渲染

| 格式 | 渲染方式 | 首次耗时 | 输出 |
|---|---|---|---|
| PSD / TIF / BMP / GIF / PNG | PIL 读合并图层（不碰图层树） | 55–450 ms | 213–537 × 760 |
| AI / PDF | pdfium 渲染首页 | 1.8–2.5 s | 166–538 × 760 |
| SVG | resvg | 70–100 ms | 760 × 760 |
| CDR | Windows Shell 缩略图 | 70 ms | 602 × 760 |
| EPS | 索引解码器（内嵌 TIFF） | 165 ms | 363 × 760 |
| Office | 直接用索引缩略图 | 5 ms | 363 × 512 |

**关键发现：PSD 的 PIL 读取快得反常。** 767 MB 的 PSD 只要 444 ms ——
PIL 只读文件末尾的合并预览，不解析图层树。（对比 psd_tools 的
`composite()`：2.7 秒打开 + 4.4 秒合成 = 7 秒，慢 15 倍，且内存吃紧。）

### 各格式的坑

**坑一：PIL 遇到 EPS 会卡 36 秒。** PIL 的 EPS 解码器会去调 Ghostscript，
本机没装，它不立刻报错而是反复找，36 秒后才失败。所以 PIL 那一层必须
限定扩展名白名单 —— 不能「先试 PIL，失败再退」。

**坑二：Office 现渲染要 8.4 秒。** 走 Word COM 导出 PDF 再渲染，用户点一下
等八秒。所以 Office 直接给索引时的缩略图（240×338），够认出是哪份文档。

**坑三：CDR 的 Shell 缩略图比自解码器好。** 自己解 zip 里的 BMP 只有
256×323；Shell 缩略图给 1014×1280。

### 缓存

按 `(路径, mtime, 大小)` 缓存渲染结果，上限 60 条，满了整体清空。
同一张图反复点：首次 55 ms → 之后 3 ms。

### 布局调整

`.detail-preview` 从 `max-height: 300px` 改成固定 `height: 420px`。
竖版海报（750×2677）在 300px 里会缩成一条 34px 宽的小条，看不出内容。
420px 下是 118px 宽，能认出画面。

**`img` 的 `max-height` 必须写具体像素**，写 `100%` 无效 ——
父级是 grid 容器，百分比高度解析不到具体值，图片会按原始比例撑开
（实测溢出到 760px）。骨架屏高度也同步改成 420px，避免图出来时面板跳动。

## 十六、卡片副标题显示修改日期（2026-11-24）

### 需求

卡片上直接看到修改时间，不用点开详情对比哪个版本更新。

### 布局

副标题改成两段式：左边说明文字（类型 / 目录 / 大小），右边日期，用 `flex` 分开。

```
节日                    2025-01-03
25.12.8                 2026-01-14
```

日期靠右固定、`tabular-nums` 等宽数字，一列卡片纵向扫下来能直接比新旧。
左侧文字 `flex:1 + min-width:0 + ellipsis`，长了自动省略；日期 `flex:none`，
永远完整显示。

### 两条试错记录

**日期格式不能混用。** 一开始做过「同年只显示 `01-14`、跨年才补 `2025-01`」
的紧凑写法，省宽度但一列里长度不齐，右对齐后左边界参差，反而更难扫。
日期用途就是比新旧，格式一致比省那几个像素重要，统一 `YYYY-MM-DD`。

**列表模式的日期会跑到屏幕最右端。** 列表模式整行很宽，`flex` 会把日期
顶到 900px 之外，中间一片空白，看着像两列不相干的信息。给 `.card-sub`
加 `max-width: 360px`，日期贴回说明文字右侧，仍在同一条竖线上。

### 悬停提示

日期上的提示气泡显示带时分的完整时间（`2025-01-03 16:06`）。卡片只有
148px 宽，放时分必然挤掉说明文字，所以完整值放 tooltip。

## 十七、画面内容搜索（2026-11-25）

### 需求

按画面内容搜图，而不是靠文件名。搜「沙滩」要能出海滩照片，搜「酒店房间」
要出客房图。用户明确说这是「画面内容文件检索」。

### 技术选型：中文 CLIP

用 `chinese-clip-vit-base-patch16` 的量化 ONNX 版（182MB）。把图片和文字
各自编码成 512 维向量，算余弦相似度。

**为什么不用原版 CLIP：** 实测原版对中文查询几乎无效。同一批图，
`'a beach'` 能正确排到第一，但用「沙滩」查出来的是随机结果 ——
原版的文本编码器只认英文 BPE，中文会被切成字面字节。

**为什么不自己训模型：** 全库 1.8 万张图，做分类器需要人工标注；
CLIP 零样本就能用，虽然精度有限但能覆盖场景。

### 实测精度

用文件名里的主题词当 ground truth，156 张平衡样本：

| 查询 | recall@5 | 说明 |
|---|---|---|
| 飞机 | 5/5 | 特征明确 |
| 美食 | 5/5 | 特征明确 |
| 寺庙 | 5/5 | 样本少（6 张） |
| 春节 | 4/5 | 红色喜庆元素可辨 |
| 沙滩 | 3/5 | 与酒店泳池易混 |
| 酒店房间 | 2/5 | 室内场景普遍相似 |
| **平均** | **80%** | |

**局限要说清楚：** 「人物」「酒店房间」这类语义宽泛的词召回偏低。
CLIP 擅长整体场景（海滩、食物、建筑），不擅长细粒度区分。
用户要的「搜人物出有人的图」这一条，实测 top5 只命中 2~3 个。

### 工程量

| 环节 | 数据 |
|---|---|
| 编码对象 | 6114 个源文件（PSD/AI/PDF/DOCX…） |
| 单张耗时 | 渲染 171ms + 推理 128ms |
| 全量 | 约 5832 张、实测 400ms/张 → 约 40 分钟（4 线程） |
| 向量存储 | 5832 × 2KB = 11MB |

**只编码源文件，不编码导出图：** 导出图多是源文件的副本，画面内容重复；
且用户搜「沙滩」是想找能改的 PSD，不是那张导出的 JPG。全库编码要多花
三倍时间却几乎没有增量信息。

### 阈值：必须相对计算

**最关键的坑。** 中文 CLIP 的余弦相似度集中在很窄的区间 —— 不同查询的
均值都在 0.29~0.34，标准差只有 0.02~0.03。

一开始写死 `min_score = 0.20`，结果是**完全不过滤**：搜「沙滩」把整个库
120 条全返回，用户看到一堆不相干的图。

改成「头名 × 比例」也不行：查询词和库里内容完全不匹配时（比如搜
「不存在的词」），头名本身也只有 0.41，按 0.86 比例切还能凑出 31 条。

最终用 **均值 + 1.3 个标准差**：
- 自适应每个查询的实际分布
- 实测各种查询保留 12~26 条，规模合理
- 「不存在的词」也会返回一些，但都集中在头部，不会铺满整屏

### 只抢一半 CPU

`threads=4` + 每批 `delay=0.04s`。实测 8 线程单张 83ms、4 线程 128ms，
但 8 线程吃满 8 个核，用户切到 PS 会明显卡。4 线程约占一半 CPU。

用 `time.sleep()` 而不是调低进程优先级：Windows 的 `SetPriorityClass`
对线程池里的工作线程不一定生效，且容易被系统重置。

### 踩过的坑

**坑一：macOS 压缩包残留导致批量编码报失败。** `._xxx.ai` 是 AppleDouble
资源分支（几百字节），pdfium 打开会抛 `PdfiumError`。更麻烦的是它会让
整批 8 张被记一次失败，用户看到「失败 4 个」以为是真问题。已在
`scanner.is_excluded()` 里排除，`EmbedJob` 里也做了二次过滤。

**坑二：渲染失败的文件没有向量。** 54 个源文件没有缩略图（旧版 AI 存的是
PostScript、Office COM 失败）。这些文件渲染不出图，但没有缩略图不代表
没内容。已加兜底：渲染失败时用索引时的缩略图（如果有）。

**坑三：`prepare_array` 的 docstring 被写坏。** 编辑时把三引号 DOC 挤到
函数名同一行，导致 `IndentationError`。已修。

### 界面

顶栏搜索框右侧加了「文件名 | 画面」切换：
- 文件名模式：原行为，走 `/api/list`，带建议补全
- 画面模式：走 `/api/semantic/search`，不提供建议（避免误导）

首次进入画面模式且索引未建时，中间区域显示引导页：说明要给多少个文件
建索引、预计多久、可以中途停。**不偷偷开始** —— 几小时的 CPU 占用必须
让用户知情。

## 十八、人物搜索：人脸检测通道（2026-11-25）

### 为什么不能靠 CLIP

CLIP 对「人物」这类词检索极差（实测 recall@5 = 2/5）。原因：CLIP 学的是
「整张图的语义氛围」，商业海报里有人有景，它更倾向匹配「海岛度假」这个
整体概念，而不是「画面里有没有人」。

补一条独立通道：用 YuNet 在人脸检测，存「这张图有几张脸」，
搜「人物」时直接按脸数过滤。

### 选型

`face_detection_yunet_2023mar.onnx`，227KB，OpenCV 自带检测器。

选它而不是 YOLO 系：YOLO 的 ONNX 权重在 HuggingFace 上都要 token
（实测 401），且最小 13MB；YuNet 227KB 单张 3~20ms，只做「有没有正脸」
这个需求足够了。

### 实测

| 指标 | 结果 |
|---|---|
| 检出准确率（名字带「人物」的图） | 4/7 有脸 |
| 误判率（图标/地图/字体类） | 1/15 |
| 单张耗时 | 3~20ms（图越大越慢） |
| 对索引速度的影响 | 无（复用 CLIP 已有的渲染图，实测 -14ms/张） |

**降低准确率的一个明确原因**：很多图是「人物纯背景」（模特被抠掉只剩背景），
文件名还带「人物」但画面里确实没人。这不是误判。

### 关键实现：复用渲染图

人脸检测放在 `semantic.encode_batch` 的 `on_image` 回调里 —— 那里刚好有
渲染好的图。单独再渲染一遍等于白扔 60% 的时间。

### 触发规则

`faces.is_person_query(text)` 判断是否走人脸通道，用**整词匹配**而不是子串：
- 「人物」「人像」「模特」「美女」「情侣」等 21 个词
- 「人间天堂」「人民」不算 —— 用 `in` 判断会把它们误伤

混合查询（如「海岛人物海报」）仍走 CLIP，因为「海岛」是更强的语义信号。

### 排序

人脸通道按**脸数降序**，不是相似度。搜「人物」是想找主体是人物的图，
一张 5 个模特的封面比一张角落有个路人的风景图更符合意图。

### 坑：OpenCV 不支持中文路径

打包目录是 `dist/溯源/`，必然带中文。OpenCV 的 ONNX 读取器把路径按
单字节处理，中文变乱码：

```
error: (-5:Bad argument) Can't read ONNX file: ...\dist\溯源\_internal\models\face_yunet.onnx
```

修法：`_ascii_copy()` 把模型复制到 `%TEMP%/itrace_yunet_<hash>.onnx` 再加载。
模型只有 227KB，复制成本可忽略。用内容哈希命名，同一份模型只复制一次。

### 阈值重调：全量索引后必须重新标定

全量 6129 张后，标准差从 0.026 降到 0.021（样本多、分布更集中），
原来 1.3σ 的结果从 12~26 条变成 600+ 条 —— 等于失效。

重新标定（以「沙滩」为例）：

| σ | 保留条数 |
|---|---|
| 1.3 | 615 |
| 1.8 | 239 |
| 2.2 | 95 |
| 2.3 | 83 |

取 2.2σ。**这是个小样本陷阱的典型案例**：阈值参数必须在全量数据上标定，
在 400 条样本上调出来的参数换到 6000 条就完全失效。

### 通过视觉核验纠正的错误判断

我先用「文件名含关键词」当 ground truth 算准确率，得出 26%~34% 的低分，
一度认为 CLIP 效果不行。把前 6 条结果的缩略图拼起来肉眼看了才发现：

- 搜「沙滩」前 6 条：5 张真的是海滩/海滩设计稿（含 3 张 BEACH PARTY 素材）
- 搜「寺庙」前 6 条：6 张全是泰国寺庙/会展中心
- 搜「美食」前 6 条：6 张全是食物
- 搜「人物」前 6 条：6 张全有真人

**文件名根本不是 ground truth** —— 库里有大量 `13.psd`、`19.psd` 这类
无意义文件名，画面是海滩但名字看不出来。用文件名评测等于把正确答案判成错的。

这一条记在这里作为教训：**评测指标本身要先验证，不能默认它可信。**

## 十九、支持任意查询词（2026-11-25）

### 结论：不限固定关键词，但原实现有三个硬伤

用中文 CLIP 编码，任何中英文输入都能算向量。但实测发现三处实现缺陷，
用户输入非短词时效果明显下降。

### 硬伤一：长句被平均成「糊向量」

「沙滩上的情侣」整串编码会把「沙滩」和「情侣」两个概念平均掉，
结果两边都不像。**这也是 CLIP 的通用问题** —— 它训练时图文对多是短句。

修法（`core/query.py`）：

1. 先把 100+ 已知场景词整体抠出来（椰子树 / 摩天轮 / 水族馆 / 会展中心…），
   避免被后续拆字破坏
2. 剩下的中文段按停用词（的 / 在 / 有 / 里 / 边 / 一个 / 一张…）切开
3. 英文/数字串单独提取
4. 最多保留 6 个候选（再多等于稀释）

**合并用 RRF，不是取最高分，也不是向量平均：**

| 方案 | 问题 |
|---|---|
| 取每条图的最高分 | 每个词各召回 50~100 条，取并集变 390 条，等于没筛 |
| 向量平均 | 互斥概念（火锅 + 海报）糊在一起，两边都不像 |
| **RRF `Σ 1/(60+rank)`** | 同时命中多个词的图得分累加，自然排前 |

最后用「相对头名的 35%」截断 —— RRF 分数的量纲取决于命中词数，
不能用绝对阈值。

### 硬伤二：英文分词完全错误

中文 CLIP 的词表里有 **9614 个带 `##` 前缀的续接 token**，表示「接在
上一个词后面的片段」。原实现把所有字符当独立词查表：

```
'beach'  -> ['be', 'ac', 'h']      ← 错，三个独立词
'beach'  -> ['beach']              ← 对，一个完整词
```

后果是向量和训练时的分布完全不一致，搜 `beach` 得到随机结果 ——
这个 bug 在只搜中文时完全看不出来。

修法：`_wordpiece()` 做最长匹配，非词首的片段加 `##` 前缀。
现在 `sunset` → `[sun, ##set]`（词表里没有完整 sunset，这是正确切法）。

### 硬伤三：混合查询被人脸通道劫持

原逻辑：命中任何人物词 → 整体切到人脸通道。
「海边的女孩」于是丢掉了「海边」，退化成「所有有人脸的图」。

改成分级处理：

| 查询类型 | 例子 | 走法 |
|---|---|---|
| 纯人物词 | 人物、模特、美女 | 人脸通道，按脸数排 |
| 混合查询 | 沙滩上的情侣、海边的女孩 | CLIP 场景 ∩ 有人脸 |
| 纯场景 | 沙滩、寺庙 | CLIP |

交集少于 3 条时放开人脸限制 —— 宁可多给几条也别给空结果。

### 界面：拆词提示条

输入长句时在结果区上方显示「拆成这些词检索：xxx」+ 后端的状态提示
（「已限定画面里必须有人」/「有人脸的匹配太少，已放宽限制」）。

不加这条提示的话，用户没法判断结果不理想是该换词，还是库里真没有。

### 能力边界的诚实说明

| 情况 | 效果 |
|---|---|
| 世界通用概念（沙滩/海豚/火锅/寺庙/飞机） | 好，前 6 条基本全对 |
| 库里有但冷门（水族馆/赛博朋克/玻璃桥） | 一般，可能靠色彩氛围蒙对 |
| 库里根本没有（企鹅/向日葵/保龄球） | **会返回不相干结果** |

**最后这条没解决。** CLIP 没有「匹配不上」的概念 —— 任何字符串都能
算出分数。试过用 `(top - mean) / std` 判断是否有真实匹配：

```
有匹配:  海豚 z=4.91  火锅 z=6.42  沙滩 z=4.70  寺庙 z=5.28
无匹配:  企鹅 z=4.21  长颈鹿 z=6.07  熊猫 z=6.21  保龄球 z=4.94
乱码:    zzz z=4.31  完全无关的词汇 z=4.84  量子纠缠 z=4.39
```

三组完全重叠，无法区分。这需要额外的「图文对是否是真实配对」判别模型
（如 BLIP 的 ITM 头），不在当前方案范围内。

**用户能感知到的表现**：搜一个库里没有的东西，会返回一些看起来
「有点相关但不完全对」的图。这是 CLIP 类检索的固有特性，不是 bug。

## 二十、图里的文字搜索（OCR，2026-11-25/26）

### 技术选型

RapidOCR 的 PP-OCRv3（13MB，纯 ONNX 不需要 paddle）。选它而不是 Tesseract：
Tesseract 对中文竖排、艺术字、海报排版几乎不可用。

渲染 1200px 长边识别。实测对比：

| 尺寸 | 耗时 | 识别段数 |
|---|---|---|
| 900px | 1.43s | 53 段 |
| 1200px | 1.52s | 52 段 |
| 1800px | 1.84s | 53 段 |

段数基本一样，但 900px 时个别小字认错（「0自费」→「0白费」），所以取 1200。

### 为什么单独一张表，不塞进 files

一张海报有 10~40 段文字，一个人一个文件对多行。存 `texts` 表
（file_id, content, score, box, model）+ `idx_texts_file` 索引。

### 检索用 LIKE，不用 FTS5 trigram

**FTS5 trigram 只支持 3 字以上查询**（实测「曼谷」「自费」都返回 0 条），
而中文两字词极多。

实测 316939 行数据下 `LIKE '%开业庆典%'` 只要 95~108ms，对用户完全无感。
少一层索引 = 少一处不一致（不用管 trigram 表和主表同步）。

### 「确认没字」的哨兵记录

识别出 0 段文字的文件也写一条 `content=''`。否则这些文件永远留在待办里，
每次点「继续」都重跑一遍纯色背景图和图标（1.5s 一个）。
查询时 `WHERE content != ''` 把它们排除。

### 按磁盘 × 格式分片（用户明确要求）

用户原话：「不要全局索引，按类型、按磁盘来，避免全库大量检索」。

界面列出每个「盘 × 格式」分片的待办量和预估耗时，用户勾选后开始。
默认选中源文件格式（PSD/AI/PDF/Word）—— 导出图多是源文件的副本，
文字内容重复，OCR 一遍是浪费。

各格式实测单张成本：

| 格式 | 耗时 | 数量 | 全量耗时 |
|---|---|---|---|
| docx | 6.35s | 243 | 26 分 |
| doc | 5.26s | 132 | 12 分 |
| psd | 1.82s | 5361 | 163 分 |
| jpg | 1.63s | 8519 | 231 分 |
| png | 0.80s | 3036 | 40 分 |

全库 18698 张约 8.2 小时。所以按需分片是必须的，不是妥协。

### 高亮定位：归一化坐标

OCR 跑在 1200px 的渲染图上，但前端预览尺寸任意（缩略图 320、详情 760、
大图 1800、原图可能 4000）。所以存 0~1 的**相对坐标**，前端用百分比定位，
不用反推缩放比。

### 踩过的坑

**1. 高亮框用主题绿看不见。** 商业海报大量用青蓝天色背景，`#2F6E5E`
（主题绿）在上面几乎不可见。改成高饱和橙红 `#FF5C33` + 白色外发光。
标注类元素的首要指标是「任何底色上都能认出」，次要才是配色协调。

**2. 344px 详情面板里框再准也没用。** 竖版长海报（1181×4098）在面板里
缩到 121px 宽，一行字高不到 6px。补了两件事：
- 每个框带序号，和下方文字列表的序号对应
- 「看大图」按钮：长边渲染到 1800px，竖版图按宽度铺开纵向滚动

**3. PyInstaller 漏打 rapidocr 的模型和配置。** 报
`config.yaml does not exist!`。需要显式打包四份：`models/` 目录、
包根 `config.yaml`、以及三个子模块各自的 `config.yaml`。

**4. PIL 默认字体没有汉字字形。** 自检里用 `ImageDraw.text` 画中文，
不指定 `msyh.ttc` 会渲染成方块，测出来必然 0 段 —— 会误判成「OCR 坏了」。

### 验证

打包版自检 7 项全过（含 `core.ocr: 识别 OK 2 段：开业庆典 Thailand`）。
界面三种模式（文件名 / 图中文 / 画面）切换正常，搜「开业庆典」140 张，
详情面板 4 个橙色框 + 4 条文字列表对应，大图模式框位置正确。

### 与华为相册的差距说明

同一个技术链条（导入时 OCR → 存文本 → 建索引 → 查询走索引），
但工程实现差三个量级：

| 维度 | 华为相册 | 本工具 |
|---|---|---|
| 算力 | NPU 专用加速 | CPU，12 核但 ORT 只用 4 线程 |
| 模型 | 端侧裁剪过的轻量模型 | PP-OCRv3 通用版（13MB） |
| 图片 | 手机照片，文字少、字大 | 设计海报，几百字、字号极小 |
| 时机 | 充电+息屏时后台增量跑 | 用户手动触发 |
| 耗时 | 每张几十毫秒 | 每张 1.5~1.8 秒 |

这 40 倍差距主要来自「图的内容不同」（海报文字量是照片的 20 倍）
和「没有 NPU」，不是算法落后。

### 补救：范围选择页进不去了（2026-11-26）

**问题（用户实际踩到）**：截图显示他在搜「五星」看结果，界面正常，但
找不到「开始识别」按钮。

**根因**：`enterTextMode()` 的判断是 `if (!st.ready) showTextSetup(st)`。
`ready` 的定义是「识别过至少 1 个文件」。我试跑时识别了 520 个，
ready 变成 true，于是**范围选择页永远不再出现** —— 剩下的 18159 个
文件没有任何入口可以补。

**这是把「首次建索引」和「继续补索引」当成一件事的错。** 索引永远是
部分的（全库 8.2 小时，用户按范围一批批跑），所以入口必须常驻。

修法两处：

1. **顶栏常驻「文字索引」按钮**，显示 `563/18720` 这样的进度，
   有待办或正在跑时亮一个小圆点。点它直接进范围页。
2. `enterTextMode()` 改成：输入框有词且有索引就直接搜，
   **否则一律进范围页** —— 不再用 ready 拦截。

顺带修了三个连带问题：
- 范围页的标题区还写着「全部文件 300/18720」，看不出自己在哪个界面
- `refreshTextStatus` 在 app.js 里被调用，但定义在 semantic.js
  （app.js 先加载先 boot）→ 报 `refreshTextStatus is not defined`，
  入口按钮因此不显示。绑定挪到 semantic.js 末尾。
- 进度页首次显示时是 `0 / 94`，因为拿到的是启动瞬间的快照，
  1.5 秒后才刷新 —— 可以接受，但把「加载 OCR 模型…」的提示
  提前显示，让用户知道在动
